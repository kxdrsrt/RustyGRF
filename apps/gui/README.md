# RustyGRF App (Tauri 2)

Desktop-Oberfläche auf dem Rust-Kern (`rgrf-core`, `rgrf-formats`). Eigenes Cargo-Workspace, damit Bibliothek, CLI und MCP-Server nicht von Tauri abhängen (Lizenzen siehe `deny.toml` und [docs/05-licensing.md](../../docs/05-licensing.md)).

## Aufbau
- `src-tauri/src/view.rs`: Filter, Sortierung und Ordnerbaum der Liste (reine Funktionen, mit Tests).
- `src-tauri/src/backend.rs`: alles, was die App mit einem Archiv tut (öffnen, suchen, blättern, Vorschau, extrahieren, prüfen), ohne Tauri-Typen, mit Tests.
- `src-tauri/src/lib.rs`: dünne Tauri-Befehle darum; schwere Arbeit läuft auf einem Arbeits-Thread, das Fenster bleibt bedienbar.
- `ui/`: reines HTML/CSS/JS (kein Build-Werkzeug). Die Liste ist virtualisiert (nur sichtbare Zeilen, Seiten vom Backend), Dark/Light per `prefers-color-scheme`. `ui/mock.js` ersetzt das Backend nur im normalen Browser, in der App ist es inaktiv.
- Namensanzeige: Standard **Koreanisch** (CP949, z. B. `유저인터페이스`), umschaltbar auf Latin-1 (so zeigt es GRF Editor) oder UTF-8. Gilt auch für die Suche; Extrahieren schreibt immer Latin-1-Namen (rundlauffähig mit `rgrf build`).
- Startpfad: `rustygrf-gui <datei.grf> [--select <suche>]` öffnet das Archiv direkt und wählt auf Wunsch den ersten Treffer der Suche (Windows/Linux reichen Dateien so an die App weiter). Ein zweiter Start gibt die Datei an die laufende App weiter (`tauri-plugin-single-instance`; Linux-only Abhängigkeiten dazu in `deny.toml` begründet).
- **„Öffnen mit“ / Doppelklick (macOS):** `.grf` und `.gpf` sind als Dokumenttypen eingetragen (`bundle.fileAssociations`, im `Info.plist` des Bundles geprüft). Gemessen: `open -g -a RustyGRF.app datei.grf` startet die App und sie hält die Datei offen (`lsof`). Offene vorgemerkte Änderungen werden vor dem Öffnen eines anderen Archivs erfragt. Unter Windows geprüft: beide Installer tragen `.grf`/`.gpf` ein, ein zweiter Start reicht die Datei an die laufende App weiter. **Nicht geprüft:** Linux-Zuordnung, Standard-App-Zuweisung im Finder.
- **Vorschau:** Bilder (BMP/JPG/PNG/GIF, **TGA** wird zu PNG gewandelt: alle 9.063 TGA der kRO-`data.grf` lesbar), Sprites (alle Bilder), Animationen (GIF je Aktion), Paletten, GAT als Bild (Begehbarkeit/Höhe), RSW/GND/RSM als Info-Text (Objekt-, Textur-, Modellzahlen), Text (kompilierte `.lub` werden dekompiliert angezeigt), Audio (WAV/MP3/OGG; die 6 ADPCM-WAVs der kRO-`data.grf` werden zu PCM gewandelt, sonst spielt nicht jedes Webview sie ab; alle 3.332 WAV abspielbar, OGG gibt es in der kRO-`data.grf` nicht, WKWebView-Wiedergabe von OGG ist ungeprüft), sonst Hex. **STR-Effekte** als GIF (Ebenen, Keys, Mischmodi, Texturen aus dem STR-Ordner oder `data\texture\effect`; vereinfacht, siehe `docs/09-formats.md`). **RSM/RSM2-Modelle in 3D** (WebGL 2 ohne Bibliothek, Maus: drehen, Rad: zoomen, Doppelklick: zurücksetzen; Beleuchtung und Drahtgitter schaltbar; Hierarchie, Texturen und Knotenanimation mit Häkchen „Animate“). **3D-Karten** (RSW/GND: Gelände mit Texturen und Lightmaps, alle Modelle der Karte instanziert, Wasser; Licht, Lightmaps, Modelle und Wasser einzeln schaltbar; Ziehen = drehen, Rechts-/Shift-Ziehen oder Pfeiltasten = bewegen, Rad = zoomen). Wasser läuft als Bildzyklus (Häkchen „Animate"). Bewegte Modelle der Karte laufen (GPU-Instancing). Wasserwellen und die Texturanimation der RSM-2.3-Modelle laufen (siehe unten).
- **Ansichten, Sortierung, Filter** (Leiste „View“): fünf Ansichten in dieser Reihenfolge (Cmd/Ctrl+1–5): **Tree** (Standard; echter Ordnerbaum mit Auf-/Zuklappen, Ordner zeigen Dateizahl und Summe, „Expand all“/„Collapse all“, Pfeiltasten: → öffnet, ← schließt oder springt zum Elternordner, Enter/Leertaste schaltet um, Doppelklick; beim Öffnen ist wie im GRF Editor `data` aufgeklappt, genauer: der einzige Ordner oberster Ebene und jeder einzelne Ordner darunter, der sonst nichts enthält), **Folders** (Ordnerbaum links, Dateien des gewählten Ordners rechts wie im GRF Editor, optional mit Unterordnern; „All files“ zeigt alles), **List** (flach: Name, Ordner, Größe) **Details** (Tabelle mit Typ, Größe, gepackter Größe; Klick auf die Spaltenköpfe sortiert) und **Gallery** (Raster mit Vorschaubildern von Bildern und Sprites; ohne Typfilter nur diese beiden Typen, die Spalten passen sich der Breite an, Pfeiltasten gehen im Raster, Vorschaubilder kommen nur für sichtbare Zellen vom Backend, `thumbnails`, und werden im Speicher gehalten). Wer schon eine andere Ansicht gewählt hatte, behält sie (die Wahl wird gespeichert). **Sortieren** nach gespeicherter Reihenfolge, Name, Pfad, Typ, Größe, gepackter Größe oder Position in der Datei, auf- oder absteigend. **Filter**: Typ (Mehrfachauswahl: Bilder, Sprites, Animationen, Paletten, Karten, Modelle, Audio, Text/Lua, Effekte, Sonstige), Größe (über/unter 1 KB bis 10 MB) und die Suche (Teilwort oder Muster wie `*.spr`); „Reset“ räumt alle auf. Im Baum öffnet eine Suche oder ein Filter alle Ordner von selbst, wenn es höchstens 3.000 Treffer gibt. Beim Umschalten von Ansicht, Sortierung und Filter bleibt der gewählte Eintrag gewählt (der Baum öffnet den Weg dorthin). Extrahieren und Entfernen wirken auf einen gewählten Ordner. Die Wahl wird gespeichert. Die Logik liegt in `src-tauri/src/view.rs` (mit Tests), die Anordnung im Backend (`set_view`, `page_view`, `tree_toggle`, `tree_set_all`, `locate`, `folder_entries`). **Gemessen** an der kRO-`data.grf` (202.358 Einträge, Release-Build): Sortieren 10–32 ms, Baum bauen 18 ms, Suche `*.spr` im Baum 52 ms, alle Ordner öffnen 1 ms (205.587 Zeilen), eine Seite 0,5 ms; mit dem echten Backend im Browser bedient (alle vier Ansichten, Sortierung, Typfilter, Ordnerwahl mit und ohne Unterordner), keine Skriptfehler.
- **Einstellungen** (Zahnrad in der Kopfleiste oder Cmd/Ctrl+,; auf jedem System gleich, gespeichert in der App): **Aussehen** (Thema System/Hell/Dunkel, Akzentfarbe Orange/Blau/Grün/Violett, Textgröße, Listendichte kompakt/normal/bequem, einfarbige Dateisymbole, Animationen aus), **beim Öffnen** (Namensanzeige, Standard-Ansicht, Vorschau-Position, letztes Archiv beim Start wieder öffnen, vor dem Verwerfen vorgemerkter Änderungen fragen) und **Bauen** (Standard für Kompression und Format im Build-Dialog); Änderungen wirken sofort, „Reset to defaults“ stellt alles zurück. Gemessen im Browser: Thema, Akzent, Textgröße und Dichte (24 → 30 px Zeilenhöhe) werden angewendet und gespeichert, Reset stellt sie her. Zusätzlich steht „Settings…“ (Cmd/Ctrl+,) im Menü der App: unter macOS im Anwendungsmenü, sonst im Bearbeiten-Menü; unter macOS und Windows im echten Fenster geprüft, Linux nicht. Das Menü wird auf jedem System vollständig selbst aufgebaut (Linux hätte sonst kein File-Menü, Windows kein View-Menü).
- **Leisten (nach Apples HIG `toolbars.md`, `settings.md`):** statt dreier Leisten eine **Hauptleiste** mit drei Gruppen (App: Einstellungen und Öffnen · Archiv: Build, Merge, Extract, Verify · Bearbeiten: Hinzufügen, Ersetzen, Entfernen, Rückgängig, Wiederholen, Änderungen mit Zähler) und rechts Suche und Vorschau-Position, darunter eine schmale **Ansichts-/Filterleiste** (Layout, Sortierung, Typ, Größe, Auf-/Zuklappen, Zurücksetzen); Namensanzeige (Korean/Latin-1/UTF-8) und Trefferzahl stehen in der Statusleiste. Symbole ohne Rahmen mit Tooltip (Name und Kürzel), Wörter erst ab 1600 px Breite; Zielgröße mindestens 30 × 30 px. **Einstellungen** stehen wunschgemäß ganz links in der Leiste; Apple rät davon ab, weil es Platz für häufige Befehle kostet (`settings.md`: Eintrag im App-Menü), deshalb gibt es zusätzlich den Menüeintrag. **Jeder Leistenbefehl steht auch im Menü** (Datei: Öffnen, Build, Merge, Extract, Verify · Bearbeiten: Datei hinzufügen, Ersetzen, Entfernen, Änderungen · Ansicht: Baum/Ordner/Liste/Details/Galerie mit Cmd/Ctrl+1–5, Vorschau-Position); ist die Schaltfläche gerade gesperrt, tut der Menübefehl nichts (der Menüeintrag selbst wird nicht ausgegraut). Das spart gegenüber vorher rund 40 px Höhe (Leisten 43 + 39 px statt 3 Zeilen).
- **Fenstergröße:** Mindestgröße 900 × 640; Hauptleiste einzeilig bei 900 px (Suche schrumpft bis 120 px). **Gemessen** (Browser, echtes Backend) in List, Folders und Tree bei 900 × 640, 1000 × 700, 1240 × 800, 1600 × 900 und 1920 × 1080: nichts außerhalb des Fensters, kein seitliches Scrollen, beide Leisten einzeilig. Die Beschriftete Fassung (ab 1600 px) habe ich nur simuliert (Wörter erzwungen bei 1440 px: passt, Suche 120 px), da der Browser keine breitere Darstellung lieferte. Im echten Fenster (macOS) geprüft: Menü-Befehle „As Tree“ und „Verify“ lösen die Aktion aus, Menüaufbau stimmt. Windows: Menü und Leiste im echten Fenster geprüft (siehe docs/11-release.md); Linux ungeprüft.
- **Im echten App-Fenster geprüft** (gebaute `.app`, macOS, per Bedienungshilfen-API und Fenster-Aufnahmen, ohne Mausereignisse): Start, Öffnen einer GRF über die Dateizuordnung (`open -a`, 24.756 Einträge), Einstellungen (Aufbau, Breite begrenzt auf 680 px), Verify-Rückfrage und -Ergebnis (Symbole Frage/Info), „Changes“-Meldung, Build und Merge starten ihre Ordner-/Dateiauswahl (nativ, nicht weiter bedient). **Nicht** im echten Fenster geprüft: Dialoge hinter einer Auswahl (Build, Merge, Extract, Add file), Editoren (ACT, Palette, Pixel, GAT), VoiceOver.
- **Karte extrahieren (2026-11-19):** In der 3D-Ansicht einer Karte (RSW) schreibt „Extract map…“ die Karte mit allen Dateien in einen Ordner (wie `rgrf map extract`, Latin-1-Namen wie beim normalen Extrahieren). Fehlende Dateien werden aufgelistet (sie können in einer anderen GRF des Clients liegen); liegen schon Dateien dort, fragt die App, ob beide behalten werden sollen. Vorher fragt ein Dialog, welche Teile mitkommen: **Modelle mit Texturen, Wasserbilder, Sounds, Minikarte, Effekte**; was in der 3D-Ansicht ausgeschaltet ist, ist dort schon abgewählt. Welt-, Boden- und Höhendatei samt Bodentexturen kommen immer mit; die Dateien werden unverändert kopiert (im Client hat die Karte also weiterhin alles, was sie nennt). Licht und Lightmaps stecken in diesen Dateien und sind nur eine Ansichtseinstellung. **Geprüft:** Backend-Test an Prontera (323 Dateien; ohne Modelle und Wasser 22 Dateien, kein `data\model`), Browser mit echtem Backend an Alberta (251 Dateien, zweiter Lauf fragt nach) und Prontera (Dialog übernimmt die Schalter, 22 geschrieben, 301 ausgelassen).
- **Karte als Bild (2026-11-19):** „Save picture…“ speichert die 3D-Ansicht so, wie sie gerade ist (Blickwinkel, ausgeschaltete Teile), als PNG in Bildschirmgröße, 2× oder 4×; größere Bilder werden in der Zielgröße neu gezeichnet, nicht hochskaliert (höchstens 8192 px Kantenlänge). „Hide all“/„Show all“ schaltet Licht, Lightmaps, Modelle und Wasser zusammen (Animate bleibt, das ist Bewegung, kein Teil). Gemessen im Browser an Prontera: Schalter einzeln und zusammen, Bild 1366 × 1052 (2×) mit Inhalt. Dabei gefunden und behoben: die Steuerzeile brach nicht um (Hinweis als schmale Spalte, „Animate“ abgeschnitten), der Hinweis steht jetzt darunter.
- **Entwurf (Absturzschutz, 2026-11-19):** Vorgemerkte Änderungen werden nach jeder Änderung, jedem Rückgängig/Wiederholen und beim Verwerfen als Entwurf im App-Datenordner gesichert (`drafts/<Hash des Archivpfads>/`: `draft.json` mit den Schritten in Reihenfolge, bearbeitete Inhalte je einmal als Datei, benannt nach MD5 und Länge; geschrieben über eine temporäre Datei). Öffnet man dasselbe Archiv wieder (nach Absturz, Schließen oder Wechsel), fragt die App: **Restore** (die Änderungen kommen als ein Rückgängig-Schritt zurück), **Discard** oder **Later** (der Entwurf wird beiseitegelegt, `drafts/<Hash>.<Zeit>/`; die Änderungen dieser Sitzung werden als eigener Entwurf gesichert; beim nächsten Öffnen kommt der neueste, danach die beiseitegelegten, einer je Öffnen, der Dialog nennt, wie viele noch folgen). Hinweise, wenn das Archiv sich seitdem geändert hat (Größe oder Änderungszeit) oder Ersatzdateien fehlen (diese werden ausgelassen). Ohne Änderungen wird der Entwurf gelöscht. **Geprüft:** Backend-Test (vormerken → neue Sitzung → angeboten, wird vor der Entscheidung nicht überschrieben → wiederherstellen ergibt dieselben Änderungen und Inhalte → speichern; Verwerfen), Modul-Tests (Hin- und Rückweg, geteilte Inhalte, fehlende Dateien, geändertes Archiv, kaputte oder fremde Entwürfe, Ausbruch aus dem Ordner), im Browser mit echtem Backend an `rdata.grf` (3 Änderungen, Seite neu geladen, Dialog, wiederhergestellt). **Nicht** im echten Fenster nach einem echten Absturz geprüft.
- **Speichern:** Diskettensymbol mit Zähler-Badge in der Bearbeiten-Gruppe, Cmd/Ctrl+S und Datei › „Save Changes as New Archive…“ öffnen die Liste der vorgemerkten Änderungen mit „Save as new archive…“. Es gibt bewusst **kein automatisches Speichern**: das geöffnete Archiv wird nie verändert (bei GRF-Dateien bis 4 GB und mehr wäre jede Änderung ein Neuschreiben); gespeichert wird immer als neue Datei. Cmd+S im Browser mit echtem Backend geprüft, Menüeintrag nicht im echten Fenster.
- **Bauoptionen erklärt:** Im Build-Dialog und in den Einstellungen steht unter Kompression und Format ein Satz zur gewählten Option (zlib = Standard für jeden Client; zopfli = dasselbe Format, kleiner, langsam; LZMA = nur Clients mit LZMA-Unterstützung; 0x200 = Standard, Grenze 4 GB; 0x300 = 64-Bit-Positionen für Archive über 4 GB, nur neuere Clients (gemessen: Warpgate-Client 2025 ja, 2020 nein); 0x102/0x103 = sehr alte Formate mit DES-Verwürfelung, ebenfalls 4 GB). „Gleiche Dateien teilen“ wird bei 0x102/0x103 gesperrt, weil dort die Verschlüsselung vom Namen abhängt. Im Browser mit echtem Backend geprüft (Dialog und Einstellungen bei 900 × 640, Auswahl wird gespeichert).
- **Meldungen:** jede Meldung und Rückfrage hat ein passendes Symbol (Information, Frage, Warnung, Fehler, Erfolg, Schloss für Passwort).
- **Icons:** alle Schaltflächen der Leisten haben ein Symbol vor dem Text (Öffnen, Bauen, Zusammenführen, Extrahieren, Prüfen, Ersetzen, Hinzufügen, Entfernen, Rückgängig, Wiederholen, Änderungen, Ansichten, Filter, Auf-/Zuklappen, Zurücksetzen), das Vorschau-Fenster und die Sortierrichtung sind reine Symbole mit Beschriftung für Screenreader. Zeilen zeigen ein Symbol je Dateityp in eigener Farbe (Bild, Sprite, Animation, Palette, Karte, Modell, Audio, Text/Lua, Effekt, Video, sonstige) und Ordner mit offenem oder geschlossenem Ordnersymbol und einem Pfeil, der sich beim Öffnen dreht (bei „reduzierte Bewegung“ ohne Drehanimation). Die Symbole sind eigene Strichzeichnungen in einem SVG-Sprite in `ui/index.html` (keine Abhängigkeit, folgen der Textfarbe). **Gemessen:** der Baum der echten kRO-`data.grf` mit allen 202.358 Einträgen (Test `the_folder_tree_holds_every_entry_once_and_opens_completely`): jeder Eintrag genau einmal, unter dem richtigen Ordner und in der richtigen Ebene, jede Ordnerzahl gleich der Zahl der Dateien darin und darunter, alles öffnen und schließen, „Weg zu einem Eintrag öffnen“ öffnet genau die Ordner auf dem Weg.
- **Tastatur und Bedienungshilfen:** Baum und Ordnerpane folgen dem WAI-ARIA-Baummuster: ↓/↑ bewegen, Home/End, Bild↑/Bild↓; **→** öffnet einen geschlossenen Ordner, springt bei einem offenen zum ersten Eintrag darin; **←** schließt einen offenen Ordner, sonst springt sie zum Elternordner (auch von einer Datei aus); **Enter** oder **Leertaste** schalten einen Ordner um; **\*** öffnet alle Ordner. Im Ordnerpane wählt jede Bewegung den Ordner (die Dateiliste rechts folgt), **Enter** setzt den Fokus in die Dateiliste. Die Trennlinien sind mit Tab erreichbar und lassen sich mit den Pfeiltasten verschieben (Umschalt: größere Schritte). Die Listen haben die Rollen `tree`/`treeitem` (mit `aria-level`, `aria-expanded`, `aria-selected`) bzw. `listbox`/`option` und `aria-activedescendant`; jede Zeile hat eine gesprochene Beschriftung („data, folder, 202,358 files, 15.14 GB, closed“), die Umschalter `aria-pressed`, Trefferzahl und Statuszeile sind `aria-live`. Gemessen mit dem echten Backend im Browser: ↓ → → → → ← ← ← Leertaste Ende Pos1 im Baum und ↓ → → ↓ → ← Enter im Ordnerpane, jeweils mit den erwarteten Zeilen, Ebenen und Zuständen im Accessibility-Baum; Bedienung mit einem echten Screenreader (VoiceOver) ungeprüft.
- **Vorschau-Fenster:** „Right“, „Bottom“ oder „Off“ (Leiste „View“, oder Cmd/Ctrl+Umschalt+P zum Aus-/Einblenden); die Trennlinien zwischen Liste und Vorschau (und zwischen Ordnerbaum und Dateien) lassen sich ziehen, die Größen werden gespeichert. Ausgeblendet lädt die App keine Vorschau.
- **Build…** packt einen Ordner zu einer GRF (zlib/0x200 als Standard, Zopfli und LZMA nur ausdrücklich gewählt), mit Fortschrittsbalken, Abbrechen und anschließender Prüfung gegen die Dateien auf der Platte. Abbruch hinterlässt keine Datei. Ein Auftrag zur Zeit.
- **Merge…** führt mehrere GRFs zu einer neuen zusammen (Reihenfolge = Priorität, per ↑/↓ änderbar; „Replace only“: letzte GRF ist die Basis, die anderen fügen keine neuen Pfade hinzu), mit Fortschritt, Abbruch, Prüfung und Statistik je Eingabe. Die Eingaben bleiben unverändert, die Ausgabe darf keine der Eingaben sein.
- **Edit-Leiste** (Replace…, Add file…, Remove, Changes (n)…): Änderungen werden gesammelt und mit „Save as new archive…“ in eine **neue** GRF geschrieben, die geöffnete bleibt unberührt. Unveränderte Einträge behalten ihre Streams (kein Neukomprimieren, die GRF wächst nicht). **Gemessen** an einer echten 88-MB-GRF (4.661 Einträge, je 1 ersetzt/hinzugefügt/entfernt): 60 ms, Ergebnis 86,7 MB, geprüft. Gleicher Pfad mehrfach → die letzte Änderung zählt. Kern: `rgrf_core::edit::apply`.
- **ACT-Editor** („Edit frames…“ in der Animationsvorschau): ein Frame als Bild (Ursprungskreuz, Anker als rote Punkte) und als Tabelle seiner Ebenen (Bildtyp und -nummer, x, y, Spiegeln, Skalierung x/y, Drehung, Farbe, Alpha, Reihenfolge ↑↓, hinzufügen/entfernen), Anker (x, y, hinzufügen/entfernen, ab ACT 2.3), Frame kopieren/entfernen/verschieben, Aktionen kopieren/entfernen/verschieben (Entfernen warnt: der Client wählt Aktionen nach Nummer), Zeit pro Frame (ms), **Sound je Frame** (Feld „Sound“ mit Liste der Sounds der Datei, leer = keiner; ab ACT 2.1), Aktionen und Frames durchblättern. **Referenzen** („Add reference…“): andere Animationen des Archivs werden mitgezeichnet, z. B. Körper und Kopf, um eine Kopfbedeckung auszurichten; je Referenz „Behind“/„In front“ und entfernen, Vorschläge für Körper und Kopf (männlich/weiblich). Jede Referenz wird so verschoben, dass ihr erster Anker auf dem ersten Anker des bearbeiteten Frames liegt (so setzt der Client Kopf und Kopfbedeckung auf den Körper); gleiche Aktion und Frame-Nummer, fehlt sie, steht der Grund daneben. Die bearbeitete Animation bleibt die Grundlage (Ursprungskreuz und Anker unverändert), Referenzen werden nie geändert, die Auswahl bleibt gespeichert. Gemessen mit dem echten Backend an `남_Crushed_Snow_Man.act` mit `초보자_남.act` und `1_남.act` dahinter (sitzt auf dem Kopf); Backend-Test auch für fehlende Referenz und die Datei selbst. **Play/Stop** spielt die Aktion mit ihrer Frame-Zeit und dabei die Sounds der Frames; der Knopf neben dem Sound-Feld hört den Sound des Frames vor. Gesucht wird wie im Client unter `data\wav\<Name>` (gemessen an `poring.act`: `poring_move.wav` usw. liegen dort); „atk“ ist im Client die Markierung des Treffer-Frames und keine Datei, die App sagt das statt „fehlt“ (gemessen: `poring.act`, Aktion 16, Frame 12 spielt `poring_attack.wav`, Frame 13 trägt „atk“). Während der Wiedergabe bleibt die Tastatur auf Play/Stop (Leertaste hält an); jede Bearbeitung hält die Wiedergabe an. Die Geschwindigkeit hängt am Rendern je Frame (im Devserver langsamer als die eingestellte Zeit bei 25 ms). Gemessen mit dem echten Backend im Browser; Escape schließt die Dialoge im echten Fenster (Windows geprüft), im eingebetteten VS-Code-Browser nicht. Jede Eingabe wird sofort vorgemerkt und das Bild neu gerendert; falsche Eingaben (Ebene/Bild/Typ außerhalb des Bereichs, unsinnige Zahlen, letzter Frame) werden abgelehnt, nie in die Datei geschrieben. Gemessen im Hintergrund an `poporing.act` der echten `data.grf`: Ebene verschieben, Frame kopieren/verschieben, Anker anlegen, Aktion kopieren (72 → 73), Zeit setzen, Aktion verschieben, entfernen (→ 72). **Rückgängig/Wiederholen:** Knöpfe „Undo“/„Redo“ in der Edit-Leiste und im ACT-Editor, Cmd/Ctrl+Z (mit Shift: wiederholen; in Textfeldern behält die Taste ihre normale Bedeutung). Jede Änderung der vorgemerkten Liste ist ein Schritt (bis 200), auch „Discard all"; eine fehlgeschlagene Änderung hinterlässt keinen Schritt und ändert nichts. Gemessen im Hintergrund an einer echten GRF: ersetzen → Undo → Redo → Cmd+Z. **Ebenen mit Maus und Tastatur:** ein Klick auf das Bild wählt die oberste Ebene, deren Pixel dort sichtbar ist (nicht nur ihr Rechteck; im Backend geprüft, `render::layer_at`), Ziehen verschiebt sie: ein gestrichelter Umriss folgt dem Zeiger 1:1, beim Loslassen wird die Verschiebung als **eine** Änderung vorgemerkt (ein Rückgängig-Schritt), ein Klick ohne Bewegung wählt nur. Mit dem Fokus auf dem Bild verschieben die Pfeiltasten die gewählte Ebene um 1 Pixel, mit Shift um 10; der Fokus bleibt dabei auf dem Bild. Die Zeilennummer in der Tabelle wählt ebenfalls. Gemessen mit dem echten Backend an `poring.act`: um (8, 4) gezogen → Versatz (0, −12) → (8, −8), dann ← und Shift+↑ → (7, −18), Rückgängig → (7, −8). Die **Anker** (rote Punkte) lassen sich ebenso ziehen (gemessen: Anker 0 von `남_Crushed_Snow_Man.act` um (3, −2) gezogen → (1, −56) → (4, −58)). **Noch nicht:** Ereignisse bearbeiten.
- **Hex-Editor und Bink-Video (2026-11-19):** „Hex…“ im Kopf jeder Vorschau zeigt die **ganze** Datei (16 Byte je Zeile, 24 Zeilen je Seite, Blättern, „Go to offset“ mit `0x400` oder dezimal) und ändert einzelne Bytes durch Eintippen von zwei Hexziffern (springt zum nächsten Byte; Ungültiges wird abgelehnt und nicht übernommen; geänderte Bytes sind markiert). „Apply changes“ merkt **eine** Änderung vor (die Größe der Datei bleibt, rückgängig wie jede andere). Gemessen im Browser an `01.bik`: tippen, ungültige Eingabe, Seitenwechsel behält Änderungen, Springen, Anwenden, erneutes Öffnen zeigt die Änderung, Rückgängig; Backend-Test. Bink-Videos (`.bik`) zeigen Größe, Bildzahl, Bildrate und Länge aus dem Kopf und einen Knopf, der die Datei in einen temporären Ordner schreibt und mit dem Programm des Systems öffnet (macOS `open`, Windows `start`, Linux `xdg-open`; im Devserver nur der Pfad). **Nicht geprüft:** ob auf deinem System ein Player für Bink installiert ist (VLC und RAD Video Tools spielen es), und das Starten selbst im echten Fenster.
- **Ansicht zurücksetzen:** Wer in der 3D-Vorschau (Karte oder Modell) weg vom Startbild gedreht, verschoben oder gezoomt hat, bekommt den Knopf „Reset view“ (zusätzlich zum Doppelklick auf das Bild); er verschwindet wieder, sobald die Ansicht am Start ist.
- **Bilder verkleinern (8 Bit):** die Vorschau einer BMP nennt die Bittiefe; bei 16/24/32 Bit zeigt „8-bit…“ das Original neben der 8-Bit-Fassung (256 Farben, Magenta bleibt exakt) mit Größe vorher/nachher und PSNR samt Erklärung, „Reduce“ merkt die Änderung vor. **„Reduce Images…“** (Menü File) schreibt eine Kopie des Archivs, in der jede 24-Bit-BMP 8 Bit wird, wo sie die gewählte Qualität hält (45/40/38/35 dB, Standard 40) und gespeichert kleiner wird; vorgemerkte Änderungen kommen mit hinein, ihre Einträge werden nicht angefasst; Fortschritt und Abbruch wie bei Merge, am Ende Bericht und „Open it“. **Gemessen** mit dem echten Backend im Browser an `rdata.grf`: Vergleich bei `com_shine_1.bmp` (214,5 → 72,5 KB, 49,5 dB), vorgemerkt, Fenstertitel „— Edited“, danach „Reduce Images…“: 5.771 + 1 vorgemerkte BMP, 20,5 MB kleiner, verifiziert, **identisch** mit `rgrf image reduce` (`diff`). Backend-Test mit eigenem Archiv. Dabei behoben: die Bilder im Vergleich waren in kleinen Fenstern abgeschnitten.
- **Pixel-Editor für Sprites** („Pixels…“ je Bild in der Sprite-Vorschau, nur Paletten-Bilder): Stift, Radierer (Farbe 0, durchsichtig), Füllen (Flächenfüllung), Pipette und Palettenwahl (256 Farben, 0 durchsichtig), Zoom, Raster, Rückgängig (bis 50 Schritte, auch Cmd/Ctrl+Z), „Revert“; Tastenkürzel P, E, F, I. Es wird auf den **Palettenindizes** gezeichnet, die Farben bleiben also genau die der Palette; die Größe des Bildes ändert sich nicht (dafür „Replace…“ mit einem PNG). Mit der Tastatur: Pfeiltasten bewegen den Cursor, Leertaste zeichnet, Umschalt+Pfeil zeichnet beim Bewegen. Die Anzeige nennt Koordinate und Farbnummer. Apply merkt das Bild vor (eine Änderung), wie jede andere. Gemessen mit dem echten Backend an `poporing.spr` (37 × 36 Pixel): Strich mit der Maus, Pixel mit der Tastatur, Apply, vorgemerkt, Palette unverändert; Backend-Test für Lesen, Schreiben, falsche Größe, falsche Daten, fehlendes Bild.
- **Wasserwellen** (3D-Karte): die Wasserfläche ist ein Gitter aus Kacheln (höchstens 200 × 200), deren Höhe im Vertex-Shader mit einem Sinus schwingt (Höhe/5, Geschwindigkeit in Grad je 1/60 s und Phase in Grad je 2 Einheiten aus der RSW-Datei; vor RSW 1.8 stehen sie nicht in der Datei, dort gelten die angenommenen Werte 1,0 / 2,0 / 50,0). **Gemessen** an echten Karten: `pay_fild01` Höhe 0,4 · Speed 3 · Phase 100, `comodo` und `prontera` 1,0 · 2 · 50, `alberta` 0,65 · 3 · 50 (Test `water_waves_of_real_maps_have_plausible_values`); die Karte rendert im Browser ohne Shader- oder Konsolenfehler. **Formel verglichen** mit dem Quelltext von roBrowsers `Water.js` (GPL, nur gelesen, nichts übernommen): Phase = Speed · Frame − 180° + Pitch · (x + z) / 2 bei 60 Frames je Sekunde, Höhe = RSW-Wert / 5. Dabei zwei Abweichungen unserer ersten Fassung gefunden und behoben (Vorzeichen durch den −180°-Versatz; Phase je 2 Einheiten statt je Gitterkachel, die bei großen Karten breiter ist). **Nicht übernommen:** roBrowsers kleine Eckenverschiebung je Dreieck (`diff`), die Wellenform ist daher bis auf diese Feinheit gleich; ein Vergleich mit dem echten Client (nur Windows-VM) steht aus. „Animate“ schaltet die Wellen mit dem Bildzyklus ab.
- **Texturanimation** (RSM 2.3, Vorschau und Karte): Spuren je Knoten und Textur mit Art 0/1 = u/v verschieben, 2/3 = u/v skalieren, 4 = drehen (Bogenmaß, um die Mitte); linear zwischen Keys, Zeit wie die Knotenanimation. **Gemessen** an der kRO-`data.grf`: 51 Modelle haben Texturanimation, 328 Spuren (Art 0: 30, 1: 280, 2: 3, 3: 4, 4: 10), letzter Key bei Frame 999. Der Viewer rechnet die Koordinaten im Vertex-Shader (Karten: je Teil eine kleine Textur mit den Transformationen). Gesehen im Browser: `spaceroad_s_03.rsm2` scrollt, mit „Animate“ aus steht das Bild still; `ba_maison.rsw` (7 Teile mit bewegten Texturen) rendert ohne Shader-/Konsolenfehler. **Nicht geprüft:** die Bedeutung der Arten und die Richtung gegen den Client (die Zuordnung der Arten 0–4 folgt der Messung der Wertebereiche, nicht einer Quelle) und die Drehachse (Mitte angenommen).
- **Kartenzellen bearbeiten** (`.gat`-Vorschau): ein Rechteck auf dem Kartenbild mit der Maus aufziehen (Koordinaten stehen als Zahlenfelder, die sich auch per Tastatur eingeben lassen; „Select all“), dann den Zelltyp (0–6 mit Namen wie im GRF Editor) und/oder die Höhe wählen und „Set cells“; die Änderung wird vorgemerkt, die Vorschau zeigt sofort das Ergebnis samt Zählung je Typ. Spielkoordinaten (x nach Osten, y nach Norden), das Bild steht darum auf dem Kopf zu den Bildzeilen. Gemessen mit dem echten Backend an `prontera.gat` (312 × 392 Zellen): Rechteck x 124–156, y 195–235 (1.353 Zellen) auf Typ 1: 997 Zellen geändert, begehbar 61.476 → 60.479; Backend-Tests für Rechteck (Ecken in beliebiger Reihenfolge), falsche Eingaben (Typ, Höhe, außerhalb der Karte) und Vormerken.
- **Paletten bearbeiten** (`.pal`-Vorschau): Klick auf eine Farbe öffnet die Farbwahl (Nr. 0 bis 255), „Adjust…“ verschiebt Farbton und skaliert Sättigung und Helligkeit eines Bereichs; beides wird vorgemerkt (Rückgängig/Wiederholen wie sonst), die Vorschau zeigt das Ergebnis. Gemessen mit dem echten Backend (Devserver) an einer `.pal` der kRO-`data.grf`: Farbe setzen und Bereich anpassen, je eine Änderung in der Liste; Backend-Test für Setzen, Anpassen und Fehleingaben.
- **Bearbeiten innerhalb von Einträgen:** in der Sprite-Vorschau „Replace…“ je Bild (PNG; bei Paletten-Sprites werden die Farben auf die Palette abgebildet, Transparenz → Index 0), in der Animationsvorschau „Set interval…“ je Aktion (ms, die Datei speichert Vielfache von 25 ms). Zusätzlich in der Sprite-Vorschau: „Add image…“ (PNG anhängen), „Remove“ je Bild (die Animation daneben, falls vorhanden, wird mit angepasst und ebenfalls vorgemerkt: Ebenen mit dem entfernten Bild werden leer, spätere rutschen nach) und „Set palette…“ (`.pal` laden). Gemessen im Hintergrund auf der echten `data.grf` (`poporing.spr`): 49 → 50 → 49 Bilder, Palette getauscht, Animation folgt, als neue GRF gespeichert (3,73 GB, verifiziert). Mehrere Änderungen am selben Eintrag bauen aufeinander auf und landen als **eine** Änderung in der Liste. Die Vorschau zeigt den Eintrag **so, wie er gespeichert würde** (inklusive vorgemerkter Änderungen, bei Animationen auch mit einem geänderten Sprite); geänderte Einträge haben in der Liste einen Akzentstreifen, entfernte sind durchgestrichen. Gemessen im Hintergrund (Devserver, echtes Backend, 4.661-Einträge-GRF): Text ersetzen → Vorschau zeigt den neuen Text → als neue GRF speichern (verifiziert, die übrigen Streams bleiben unverändert) → öffnen → neuer Text.
- Einziges npm-Paket: `@tauri-apps/cli` (Entwicklungsabhängigkeit).

## Starten und Bauen
```
cd apps/gui
npm install                  # holt nur die Tauri-CLI
npx tauri dev                # Fenster mit der App
npx tauri build              # Installer/Bundle für das eigene System
cargo test                   # Backend-Tests (Tests mit echten Archiven brauchen RGRF_TESTDATA)
```
Das Bauverzeichnis steht lokal in `.cargo/config.toml` (nicht im Git).
**Prüfen ohne Fenster (Hintergrund):** `cargo run --features devserver --bin devserver -- ui 8766` startet die echte Oberfläche mit dem echten Backend auf `http://127.0.0.1:8766/` (nur localhost, nur für die Entwicklung). Ein Browser, auch ein automatisierter, kann sie bedienen, ohne dass ein Fenster aufgeht; Dateidialoge beantwortet eine Warteschlange (`window.__dialogs.push("/pfad")` vor dem Klick). Fortschrittsanzeigen laufen dort nicht.
Layout ohne App ausprobieren: `python3 -m http.server -d ui 8765`, dann `http://127.0.0.1:8765` öffnen (Mock-Daten).
