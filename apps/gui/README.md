# RustyGRF App (Tauri 2)

Desktop-Oberfläche auf dem Rust-Kern (`rgrf-core`, `rgrf-formats`). Eigenes Cargo-Workspace, damit Bibliothek, CLI und MCP-Server nicht von Tauri abhängen (Lizenzen siehe `deny.toml` und [docs/05-licensing.md](../../docs/05-licensing.md)).

## Aufbau
- `src-tauri/src/backend.rs`: alles, was die App mit einem Archiv tut (öffnen, suchen, blättern, Vorschau, extrahieren, prüfen), ohne Tauri-Typen, mit Tests.
- `src-tauri/src/lib.rs`: dünne Tauri-Befehle darum; schwere Arbeit läuft auf einem Arbeits-Thread, das Fenster bleibt bedienbar.
- `ui/`: reines HTML/CSS/JS (kein Build-Werkzeug). Die Liste ist virtualisiert (nur sichtbare Zeilen, Seiten vom Backend), Dark/Light per `prefers-color-scheme`. `ui/mock.js` ersetzt das Backend nur im normalen Browser, in der App ist es inaktiv.
- Namensanzeige: Standard **Koreanisch** (CP949, z. B. `유저인터페이스`), umschaltbar auf Latin-1 (so zeigt es GRF Editor) oder UTF-8. Gilt auch für die Suche; Extrahieren schreibt immer Latin-1-Namen (rundlauffähig mit `rgrf build`).
- Startpfad: `rustygrf-gui <datei.grf> [--select <suche>]` öffnet das Archiv direkt und wählt auf Wunsch den ersten Treffer der Suche (Windows/Linux reichen Dateien so an die App weiter).
- **„Öffnen mit“ / Doppelklick (macOS):** `.grf` und `.gpf` sind als Dokumenttypen eingetragen (`bundle.fileAssociations`, im `Info.plist` des Bundles geprüft). Gemessen: `open -g -a RustyGRF.app datei.grf` startet die App und sie hält die Datei offen (`lsof`). Offene vorgemerkte Änderungen werden vor dem Öffnen eines anderen Archivs erfragt. **Nicht geprüft:** Windows/Linux-Zuordnung, Standard-App-Zuweisung im Finder, ein zweiter Start bei laufender App (öffnet einen zweiten Prozess; Single-Instance fehlt noch).
- **Vorschau:** Bilder (BMP/JPG/PNG/GIF, **TGA** wird zu PNG gewandelt: alle 9.063 TGA der kRO-`data.grf` lesbar), Sprites (alle Bilder), Animationen (GIF je Aktion), Paletten, GAT als Bild (Begehbarkeit/Höhe), RSW/GND/RSM als Info-Text (Objekt-, Textur-, Modellzahlen), Text, Audio (WAV/MP3/OGG; die 6 ADPCM-WAVs der kRO-`data.grf` werden zu PCM gewandelt, sonst spielt nicht jedes Webview sie ab; alle 3.332 WAV abspielbar, OGG gibt es in der kRO-`data.grf` nicht, WKWebView-Wiedergabe von OGG ist ungeprüft), sonst Hex. **Keine** 3D-Ansicht von Karten/Modellen und kein STR-Effekt-Viewer.
- **Build…** packt einen Ordner zu einer GRF (zlib/0x200 als Standard, Zopfli und LZMA nur ausdrücklich gewählt), mit Fortschrittsbalken, Abbrechen und anschließender Prüfung gegen die Dateien auf der Platte. Abbruch hinterlässt keine Datei. Ein Auftrag zur Zeit.
- **Merge…** führt mehrere GRFs zu einer neuen zusammen (Reihenfolge = Priorität, per ↑/↓ änderbar; „Replace only“: letzte GRF ist die Basis, die anderen fügen keine neuen Pfade hinzu), mit Fortschritt, Abbruch, Prüfung und Statistik je Eingabe. Die Eingaben bleiben unverändert, die Ausgabe darf keine der Eingaben sein.
- **Edit-Leiste** (Replace…, Add file…, Remove, Changes (n)…): Änderungen werden gesammelt und mit „Save as new archive…“ in eine **neue** GRF geschrieben, die geöffnete bleibt unberührt. Unveränderte Einträge behalten ihre Streams (kein Neukomprimieren, die GRF wächst nicht). **Gemessen** an einer echten 88-MB-GRF (4.661 Einträge, je 1 ersetzt/hinzugefügt/entfernt): 60 ms, Ergebnis 86,7 MB, geprüft. Gleicher Pfad mehrfach → die letzte Änderung zählt. Kern: `rgrf_core::edit::apply`.
- **ACT-Editor** („Edit frames…“ in der Animationsvorschau): ein Frame als Bild (Ursprungskreuz, Anker als rote Punkte) und als Tabelle seiner Ebenen (Bildtyp und -nummer, x, y, Spiegeln, Skalierung x/y, Drehung, Farbe, Alpha, Reihenfolge ↑↓, hinzufügen/entfernen), Anker (x, y, hinzufügen/entfernen, ab ACT 2.3), Frame kopieren/entfernen/verschieben, Aktionen kopieren/entfernen/verschieben (Entfernen warnt: der Client wählt Aktionen nach Nummer), Zeit pro Frame (ms), Aktionen und Frames durchblättern. Jede Eingabe wird sofort vorgemerkt und das Bild neu gerendert; falsche Eingaben (Ebene/Bild/Typ außerhalb des Bereichs, unsinnige Zahlen, letzter Frame) werden abgelehnt, nie in die Datei geschrieben. Gemessen im Hintergrund an `poporing.act` der echten `data.grf`: Ebene verschieben, Frame kopieren/verschieben, Anker anlegen, Aktion kopieren (72 → 73), Zeit setzen, Aktion verschieben, entfernen (→ 72). **Rückgängig/Wiederholen:** Knöpfe „Undo“/„Redo“ in der Edit-Leiste und im ACT-Editor, Cmd/Ctrl+Z (mit Shift: wiederholen; in Textfeldern behält die Taste ihre normale Bedeutung). Jede Änderung der vorgemerkten Liste ist ein Schritt (bis 200), auch „Discard all"; eine fehlgeschlagene Änderung hinterlässt keinen Schritt und ändert nichts. Gemessen im Hintergrund an einer echten GRF: ersetzen → Undo → Redo → Cmd+Z. **Noch nicht:** Ebenen mit der Maus ziehen, Sounds und Ereignisse bearbeiten.
- **Bearbeiten innerhalb von Einträgen:** in der Sprite-Vorschau „Replace…“ je Bild (PNG; bei Paletten-Sprites werden die Farben auf die Palette abgebildet, Transparenz → Index 0), in der Animationsvorschau „Set interval…“ je Aktion (ms, die Datei speichert Vielfache von 25 ms). Zusätzlich in der Sprite-Vorschau: „Add image…“ (PNG anhängen), „Remove“ je Bild (die Animation daneben, falls vorhanden, wird mit angepasst und ebenfalls vorgemerkt: Ebenen mit dem entfernten Bild werden leer, spätere rutschen nach) und „Set palette…“ (`.pal` laden). Gemessen im Hintergrund auf der echten `data.grf` (`poporing.spr`): 49 → 50 → 49 Bilder, Palette getauscht, Animation folgt, als neue GRF gespeichert (3,73 GB, verifiziert). Mehrere Änderungen am selben Eintrag bauen aufeinander auf und landen als **eine** Änderung in der Liste. Die Vorschau zeigt den Eintrag **so, wie er gespeichert würde** (inklusive vorgemerkter Änderungen, bei Animationen auch mit einem geänderten Sprite); geänderte Einträge haben in der Liste einen Akzentstreifen, entfernte sind durchgestrichen. Gemessen im Hintergrund (Devserver, echtes Backend, 4.661-Einträge-GRF): Text ersetzen → Vorschau zeigt den neuen Text → als neue GRF speichern (verifiziert, die übrigen Streams bleiben unverändert) → öffnen → neuer Text.
- Einziges npm-Paket: `@tauri-apps/cli` (Entwicklungsabhängigkeit).

## Starten und Bauen
```
cd apps/gui
npm install                  # holt nur die Tauri-CLI
npx tauri dev                # Fenster mit der App
npx tauri build              # Installer/Bundle für das eigene System
cargo test                   # Backend-Tests (Tests mit echten Archiven brauchen RGRF_TESTDATA)
```
Das Bauverzeichnis steht lokal in `.cargo/config.toml` (nicht im Git).
**Prüfen ohne Fenster (Hintergrund):** `cargo run --features devserver --bin devserver -- ui 8766` startet die echte Oberfläche mit dem echten Backend auf `http://127.0.0.1:8766/` (nur localhost, nur für die Entwicklung). Ein Browser, auch ein automatisierter, kann sie bedienen, ohne dass ein Fenster aufgeht; Dateidialoge beantwortet eine Warteschlange (`window.__dialogs.push("/pfad")` vor dem Klick). Fortschrittsanzeigen laufen dort nicht.
Layout ohne App ausprobieren: `python3 -m http.server -d ui 8765`, dann `http://127.0.0.1:8765` öffnen (Mock-Daten).
