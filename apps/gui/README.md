# RustyGRF App (Tauri 2)

Desktop-Oberfläche auf dem Rust-Kern (`rgrf-core`, `rgrf-formats`). Eigenes Cargo-Workspace, damit Bibliothek, CLI und MCP-Server nicht von Tauri abhängen (Lizenzen siehe `deny.toml` und [docs/05-licensing.md](../../docs/05-licensing.md)).

## Aufbau
- `src-tauri/src/view.rs`: Filter, Sortierung und Ordnerbaum der Liste (reine Funktionen, mit Tests).
- `src-tauri/src/backend.rs`: alles, was die App mit einem Archiv tut (öffnen, suchen, blättern, Vorschau, extrahieren, prüfen), ohne Tauri-Typen, mit Tests.
- `src-tauri/src/lib.rs`: dünne Tauri-Befehle darum; schwere Arbeit läuft auf einem Arbeits-Thread, das Fenster bleibt bedienbar.
- `ui/`: reines HTML/CSS/JS (kein Build-Werkzeug). Die Liste ist virtualisiert (nur sichtbare Zeilen, Seiten vom Backend), Dark/Light per `prefers-color-scheme`. `ui/mock.js` ersetzt das Backend nur im normalen Browser, in der App ist es inaktiv.
- Namensanzeige: Standard **Koreanisch** (CP949, z. B. `유저인터페이스`), umschaltbar auf Latin-1 (so zeigt es GRF Editor) oder UTF-8. Gilt auch für die Suche; Extrahieren schreibt immer Latin-1-Namen (rundlauffähig mit `rgrf build`).
- Startpfad: `rustygrf-gui <datei.grf> [--select <suche>]` öffnet das Archiv direkt und wählt auf Wunsch den ersten Treffer der Suche (Windows/Linux reichen Dateien so an die App weiter). Ein zweiter Start gibt die Datei an die laufende App weiter (`tauri-plugin-single-instance`; Linux-only Abhängigkeiten dazu in `deny.toml` begründet).
- **„Öffnen mit“ / Doppelklick (macOS):** `.grf` und `.gpf` sind als Dokumenttypen eingetragen (`bundle.fileAssociations`, im `Info.plist` des Bundles geprüft). Gemessen: `open -g -a RustyGRF.app datei.grf` startet die App und sie hält die Datei offen (`lsof`). Offene vorgemerkte Änderungen werden vor dem Öffnen eines anderen Archivs erfragt. **Nicht geprüft:** Windows/Linux-Zuordnung, Standard-App-Zuweisung im Finder, ein zweiter Start bei laufender App (öffnet einen zweiten Prozess; Single-Instance fehlt noch).
- **Vorschau:** Bilder (BMP/JPG/PNG/GIF, **TGA** wird zu PNG gewandelt: alle 9.063 TGA der kRO-`data.grf` lesbar), Sprites (alle Bilder), Animationen (GIF je Aktion), Paletten, GAT als Bild (Begehbarkeit/Höhe), RSW/GND/RSM als Info-Text (Objekt-, Textur-, Modellzahlen), Text (kompilierte `.lub` werden dekompiliert angezeigt), Audio (WAV/MP3/OGG; die 6 ADPCM-WAVs der kRO-`data.grf` werden zu PCM gewandelt, sonst spielt nicht jedes Webview sie ab; alle 3.332 WAV abspielbar, OGG gibt es in der kRO-`data.grf` nicht, WKWebView-Wiedergabe von OGG ist ungeprüft), sonst Hex. **STR-Effekte** als GIF (Ebenen, Keys, Mischmodi, Texturen aus dem STR-Ordner oder `data\texture\effect`; vereinfacht, siehe `docs/09-formats.md`). **RSM/RSM2-Modelle in 3D** (WebGL 2 ohne Bibliothek, Maus: drehen, Rad: zoomen, Doppelklick: zurücksetzen; Beleuchtung und Drahtgitter schaltbar; Hierarchie, Texturen und Knotenanimation mit Häkchen „Animate“). **3D-Karten** (RSW/GND: Gelände mit Texturen und Lightmaps, alle Modelle der Karte instanziert, Wasser; Licht, Lightmaps, Modelle und Wasser einzeln schaltbar; Ziehen = drehen, Rechts-/Shift-Ziehen oder Pfeiltasten = bewegen, Rad = zoomen). Wasser läuft als Bildzyklus (Häkchen „Animate"). Bewegte Modelle der Karte laufen (GPU-Instancing). Wasserwellen und die Texturanimation der RSM-2.3-Modelle laufen (siehe unten).
- **Ansichten, Sortierung, Filter** (Leiste „View“): vier Ansichten, **List** (flach: Name, Ordner, Größe), **Details** (Tabelle mit Typ, Größe, gepackter Größe; Klick auf die Spaltenköpfe sortiert), **Tree** (echter Ordnerbaum mit Auf-/Zuklappen, Ordner zeigen Dateizahl und Summe, „Expand all“/„Collapse all“, Pfeiltasten: → öffnet, ← schließt oder springt zum Elternordner, Enter/Leertaste schaltet um, Doppelklick) und **Folders** (Ordnerbaum links, Dateien des gewählten Ordners rechts wie im GRF Editor, optional mit Unterordnern; „All files“ zeigt alles). **Sortieren** nach gespeicherter Reihenfolge, Name, Pfad, Typ, Größe, gepackter Größe oder Position in der Datei, auf- oder absteigend. **Filter**: Typ (Mehrfachauswahl: Bilder, Sprites, Animationen, Paletten, Karten, Modelle, Audio, Text/Lua, Effekte, Sonstige), Größe (über/unter 1 KB bis 10 MB) und die Suche (Teilwort oder Muster wie `*.spr`); „Reset“ räumt alle auf. Im Baum öffnet eine Suche oder ein Filter alle Ordner von selbst, wenn es höchstens 3.000 Treffer gibt. Beim Umschalten von Ansicht, Sortierung und Filter bleibt der gewählte Eintrag gewählt (der Baum öffnet den Weg dorthin). Extrahieren und Entfernen wirken auf einen gewählten Ordner. Die Wahl wird gespeichert. Die Logik liegt in `src-tauri/src/view.rs` (mit Tests), die Anordnung im Backend (`set_view`, `page_view`, `tree_toggle`, `tree_set_all`, `locate`, `folder_entries`). **Gemessen** an der kRO-`data.grf` (202.358 Einträge, Release-Build): Sortieren 10–32 ms, Baum bauen 18 ms, Suche `*.spr` im Baum 52 ms, alle Ordner öffnen 1 ms (205.587 Zeilen), eine Seite 0,5 ms; mit dem echten Backend im Browser bedient (alle vier Ansichten, Sortierung, Typfilter, Ordnerwahl mit und ohne Unterordner), keine Skriptfehler.
- **Einstellungen** (Zahnrad in der Kopfleiste oder Cmd/Ctrl+,; auf jedem System gleich, gespeichert in der App): **Aussehen** (Thema System/Hell/Dunkel, Akzentfarbe Orange/Blau/Grün/Violett, Textgröße, Listendichte kompakt/normal/bequem, einfarbige Dateisymbole, Animationen aus), **beim Öffnen** (Namensanzeige, Standard-Ansicht, Vorschau-Position, letztes Archiv beim Start wieder öffnen, vor dem Verwerfen vorgemerkter Änderungen fragen) und **Bauen** (Standard für Kompression und Format im Build-Dialog); Änderungen wirken sofort, „Reset to defaults“ stellt alles zurück. Gemessen im Browser: Thema, Akzent, Textgröße und Dichte (24 → 30 px Zeilenhöhe) werden angewendet und gespeichert, Reset stellt sie her. Kein natives Menü „Einstellungen…“ unter macOS (nur Zahnrad und Tastenkürzel).
- **Fenstergröße und Layout:** Mindestgröße 900 × 640; die Leisten brechen um, unter 1180 px Breite zeigen die Schaltflächen nur ihr Symbol (Name als Tooltip und für Screenreader), unter 1000 px auch die Ansichtsumschalter und Beschriftungen. **Gemessen** (Browser, echtes Backend) bei 900 × 600, 1024 × 700, 1240 × 800 und 1600 × 1000 sowie in List/Details/Tree/Folders: nichts außerhalb des Fensters, nichts überlappt, kein seitliches Scrollen. Dabei gefunden und behoben: vorher liefen die Leisten schon bei 1024 px über den Rand (Extract, Verify und Zahnrad abgeschnitten).
- **Im echten App-Fenster geprüft** (gebaute `.app`, macOS, per Bedienungshilfen-API und Fenster-Aufnahmen, ohne Mausereignisse): Start, Öffnen einer GRF über die Dateizuordnung (`open -a`, 24.756 Einträge), Einstellungen (Aufbau, Breite begrenzt auf 680 px), Verify-Rückfrage und -Ergebnis (Symbole Frage/Info), „Changes“-Meldung, Build und Merge starten ihre Ordner-/Dateiauswahl (nativ, nicht weiter bedient). **Nicht** im echten Fenster geprüft: Dialoge hinter einer Auswahl (Build, Merge, Extract, Add file), Editoren (ACT, Palette, Pixel, GAT), VoiceOver.
- **Meldungen:** jede Meldung und Rückfrage hat ein passendes Symbol (Information, Frage, Warnung, Fehler, Erfolg, Schloss für Passwort).
- **Icons:** alle Schaltflächen der Leisten haben ein Symbol vor dem Text (Öffnen, Bauen, Zusammenführen, Extrahieren, Prüfen, Ersetzen, Hinzufügen, Entfernen, Rückgängig, Wiederholen, Änderungen, Ansichten, Filter, Auf-/Zuklappen, Zurücksetzen), das Vorschau-Fenster und die Sortierrichtung sind reine Symbole mit Beschriftung für Screenreader. Zeilen zeigen ein Symbol je Dateityp in eigener Farbe (Bild, Sprite, Animation, Palette, Karte, Modell, Audio, Text/Lua, Effekt, Video, sonstige) und Ordner mit offenem oder geschlossenem Ordnersymbol und einem Pfeil, der sich beim Öffnen dreht (bei „reduzierte Bewegung“ ohne Drehanimation). Die Symbole sind eigene Strichzeichnungen in einem SVG-Sprite in `ui/index.html` (keine Abhängigkeit, folgen der Textfarbe). **Gemessen:** der Baum der echten kRO-`data.grf` mit allen 202.358 Einträgen (Test `the_folder_tree_holds_every_entry_once_and_opens_completely`): jeder Eintrag genau einmal, unter dem richtigen Ordner und in der richtigen Ebene, jede Ordnerzahl gleich der Zahl der Dateien darin und darunter, alles öffnen und schließen, „Weg zu einem Eintrag öffnen“ öffnet genau die Ordner auf dem Weg.
- **Tastatur und Bedienungshilfen:** Baum und Ordnerpane folgen dem WAI-ARIA-Baummuster: ↓/↑ bewegen, Home/End, Bild↑/Bild↓; **→** öffnet einen geschlossenen Ordner, springt bei einem offenen zum ersten Eintrag darin; **←** schließt einen offenen Ordner, sonst springt sie zum Elternordner (auch von einer Datei aus); **Enter** oder **Leertaste** schalten einen Ordner um; **\*** öffnet alle Ordner. Im Ordnerpane wählt jede Bewegung den Ordner (die Dateiliste rechts folgt), **Enter** setzt den Fokus in die Dateiliste. Die Trennlinien sind mit Tab erreichbar und lassen sich mit den Pfeiltasten verschieben (Umschalt: größere Schritte). Die Listen haben die Rollen `tree`/`treeitem` (mit `aria-level`, `aria-expanded`, `aria-selected`) bzw. `listbox`/`option` und `aria-activedescendant`; jede Zeile hat eine gesprochene Beschriftung („data, folder, 202,358 files, 15.14 GB, closed“), die Umschalter `aria-pressed`, Trefferzahl und Statuszeile sind `aria-live`. Gemessen mit dem echten Backend im Browser: ↓ → → → → ← ← ← Leertaste Ende Pos1 im Baum und ↓ → → ↓ → ← Enter im Ordnerpane, jeweils mit den erwarteten Zeilen, Ebenen und Zuständen im Accessibility-Baum; Bedienung mit einem echten Screenreader (VoiceOver) ungeprüft.
- **Vorschau-Fenster:** „Right“, „Bottom“ oder „Off“ (Leiste „View“, oder Cmd/Ctrl+Umschalt+P zum Aus-/Einblenden); die Trennlinien zwischen Liste und Vorschau (und zwischen Ordnerbaum und Dateien) lassen sich ziehen, die Größen werden gespeichert. Ausgeblendet lädt die App keine Vorschau.
- **Build…** packt einen Ordner zu einer GRF (zlib/0x200 als Standard, Zopfli und LZMA nur ausdrücklich gewählt), mit Fortschrittsbalken, Abbrechen und anschließender Prüfung gegen die Dateien auf der Platte. Abbruch hinterlässt keine Datei. Ein Auftrag zur Zeit.
- **Merge…** führt mehrere GRFs zu einer neuen zusammen (Reihenfolge = Priorität, per ↑/↓ änderbar; „Replace only“: letzte GRF ist die Basis, die anderen fügen keine neuen Pfade hinzu), mit Fortschritt, Abbruch, Prüfung und Statistik je Eingabe. Die Eingaben bleiben unverändert, die Ausgabe darf keine der Eingaben sein.
- **Edit-Leiste** (Replace…, Add file…, Remove, Changes (n)…): Änderungen werden gesammelt und mit „Save as new archive…“ in eine **neue** GRF geschrieben, die geöffnete bleibt unberührt. Unveränderte Einträge behalten ihre Streams (kein Neukomprimieren, die GRF wächst nicht). **Gemessen** an einer echten 88-MB-GRF (4.661 Einträge, je 1 ersetzt/hinzugefügt/entfernt): 60 ms, Ergebnis 86,7 MB, geprüft. Gleicher Pfad mehrfach → die letzte Änderung zählt. Kern: `rgrf_core::edit::apply`.
- **ACT-Editor** („Edit frames…“ in der Animationsvorschau): ein Frame als Bild (Ursprungskreuz, Anker als rote Punkte) und als Tabelle seiner Ebenen (Bildtyp und -nummer, x, y, Spiegeln, Skalierung x/y, Drehung, Farbe, Alpha, Reihenfolge ↑↓, hinzufügen/entfernen), Anker (x, y, hinzufügen/entfernen, ab ACT 2.3), Frame kopieren/entfernen/verschieben, Aktionen kopieren/entfernen/verschieben (Entfernen warnt: der Client wählt Aktionen nach Nummer), Zeit pro Frame (ms), **Sound je Frame** (Feld „Sound“ mit Liste der Sounds der Datei, leer = keiner; ab ACT 2.1), Aktionen und Frames durchblättern. Jede Eingabe wird sofort vorgemerkt und das Bild neu gerendert; falsche Eingaben (Ebene/Bild/Typ außerhalb des Bereichs, unsinnige Zahlen, letzter Frame) werden abgelehnt, nie in die Datei geschrieben. Gemessen im Hintergrund an `poporing.act` der echten `data.grf`: Ebene verschieben, Frame kopieren/verschieben, Anker anlegen, Aktion kopieren (72 → 73), Zeit setzen, Aktion verschieben, entfernen (→ 72). **Rückgängig/Wiederholen:** Knöpfe „Undo“/„Redo“ in der Edit-Leiste und im ACT-Editor, Cmd/Ctrl+Z (mit Shift: wiederholen; in Textfeldern behält die Taste ihre normale Bedeutung). Jede Änderung der vorgemerkten Liste ist ein Schritt (bis 200), auch „Discard all"; eine fehlgeschlagene Änderung hinterlässt keinen Schritt und ändert nichts. Gemessen im Hintergrund an einer echten GRF: ersetzen → Undo → Redo → Cmd+Z. **Noch nicht:** Ebenen mit der Maus ziehen, Ereignisse bearbeiten.
- **Pixel-Editor für Sprites** („Pixels…“ je Bild in der Sprite-Vorschau, nur Paletten-Bilder): Stift, Radierer (Farbe 0, durchsichtig), Füllen (Flächenfüllung), Pipette und Palettenwahl (256 Farben, 0 durchsichtig), Zoom, Raster, Rückgängig (bis 50 Schritte, auch Cmd/Ctrl+Z), „Revert“; Tastenkürzel P, E, F, I. Es wird auf den **Palettenindizes** gezeichnet, die Farben bleiben also genau die der Palette; die Größe des Bildes ändert sich nicht (dafür „Replace…“ mit einem PNG). Mit der Tastatur: Pfeiltasten bewegen den Cursor, Leertaste zeichnet, Umschalt+Pfeil zeichnet beim Bewegen. Die Anzeige nennt Koordinate und Farbnummer. Apply merkt das Bild vor (eine Änderung), wie jede andere. Gemessen mit dem echten Backend an `poporing.spr` (37 × 36 Pixel): Strich mit der Maus, Pixel mit der Tastatur, Apply, vorgemerkt, Palette unverändert; Backend-Test für Lesen, Schreiben, falsche Größe, falsche Daten, fehlendes Bild.
- **Wasserwellen** (3D-Karte): die Wasserfläche ist ein Gitter aus Kacheln (höchstens 200 × 200), deren Höhe im Vertex-Shader mit einem Sinus schwingt (Höhe/5, Geschwindigkeit in Grad je 1/60 s und Phase in Grad je 2 Einheiten aus der RSW-Datei; vor RSW 1.8 stehen sie nicht in der Datei, dort gelten die angenommenen Werte 1,0 / 2,0 / 50,0). **Gemessen** an echten Karten: `pay_fild01` Höhe 0,4 · Speed 3 · Phase 100, `comodo` und `prontera` 1,0 · 2 · 50, `alberta` 0,65 · 3 · 50 (Test `water_waves_of_real_maps_have_plausible_values`); die Karte rendert im Browser ohne Shader- oder Konsolenfehler. **Formel verglichen** mit dem Quelltext von roBrowsers `Water.js` (GPL, nur gelesen, nichts übernommen): Phase = Speed · Frame − 180° + Pitch · (x + z) / 2 bei 60 Frames je Sekunde, Höhe = RSW-Wert / 5. Dabei zwei Abweichungen unserer ersten Fassung gefunden und behoben (Vorzeichen durch den −180°-Versatz; Phase je 2 Einheiten statt je Gitterkachel, die bei großen Karten breiter ist). **Nicht übernommen:** roBrowsers kleine Eckenverschiebung je Dreieck (`diff`), die Wellenform ist daher bis auf diese Feinheit gleich; ein Vergleich mit dem echten Client (nur Windows-VM) steht aus. „Animate“ schaltet die Wellen mit dem Bildzyklus ab.
- **Texturanimation** (RSM 2.3, Vorschau und Karte): Spuren je Knoten und Textur mit Art 0/1 = u/v verschieben, 2/3 = u/v skalieren, 4 = drehen (Bogenmaß, um die Mitte); linear zwischen Keys, Zeit wie die Knotenanimation. **Gemessen** an der kRO-`data.grf`: 51 Modelle haben Texturanimation, 328 Spuren (Art 0: 30, 1: 280, 2: 3, 3: 4, 4: 10), letzter Key bei Frame 999. Der Viewer rechnet die Koordinaten im Vertex-Shader (Karten: je Teil eine kleine Textur mit den Transformationen). Gesehen im Browser: `spaceroad_s_03.rsm2` scrollt, mit „Animate“ aus steht das Bild still; `ba_maison.rsw` (7 Teile mit bewegten Texturen) rendert ohne Shader-/Konsolenfehler. **Nicht geprüft:** die Bedeutung der Arten und die Richtung gegen den Client (die Zuordnung der Arten 0–4 folgt der Messung der Wertebereiche, nicht einer Quelle) und die Drehachse (Mitte angenommen).
- **Kartenzellen bearbeiten** (`.gat`-Vorschau): ein Rechteck auf dem Kartenbild mit der Maus aufziehen (Koordinaten stehen als Zahlenfelder, die sich auch per Tastatur eingeben lassen; „Select all“), dann den Zelltyp (0–6 mit Namen wie im GRF Editor) und/oder die Höhe wählen und „Set cells“; die Änderung wird vorgemerkt, die Vorschau zeigt sofort das Ergebnis samt Zählung je Typ. Spielkoordinaten (x nach Osten, y nach Norden), das Bild steht darum auf dem Kopf zu den Bildzeilen. Gemessen mit dem echten Backend an `prontera.gat` (312 × 392 Zellen): Rechteck x 124–156, y 195–235 (1.353 Zellen) auf Typ 1: 997 Zellen geändert, begehbar 61.476 → 60.479; Backend-Tests für Rechteck (Ecken in beliebiger Reihenfolge), falsche Eingaben (Typ, Höhe, außerhalb der Karte) und Vormerken.
- **Paletten bearbeiten** (`.pal`-Vorschau): Klick auf eine Farbe öffnet die Farbwahl (Nr. 0 bis 255), „Adjust…“ verschiebt Farbton und skaliert Sättigung und Helligkeit eines Bereichs; beides wird vorgemerkt (Rückgängig/Wiederholen wie sonst), die Vorschau zeigt das Ergebnis. Gemessen mit dem echten Backend (Devserver) an einer `.pal` der kRO-`data.grf`: Farbe setzen und Bereich anpassen, je eine Änderung in der Liste; Backend-Test für Setzen, Anpassen und Fehleingaben.
- **Bearbeiten innerhalb von Einträgen:** in der Sprite-Vorschau „Replace…“ je Bild (PNG; bei Paletten-Sprites werden die Farben auf die Palette abgebildet, Transparenz → Index 0), in der Animationsvorschau „Set interval…“ je Aktion (ms, die Datei speichert Vielfache von 25 ms). Zusätzlich in der Sprite-Vorschau: „Add image…“ (PNG anhängen), „Remove“ je Bild (die Animation daneben, falls vorhanden, wird mit angepasst und ebenfalls vorgemerkt: Ebenen mit dem entfernten Bild werden leer, spätere rutschen nach) und „Set palette…“ (`.pal` laden). Gemessen im Hintergrund auf der echten `data.grf` (`poporing.spr`): 49 → 50 → 49 Bilder, Palette getauscht, Animation folgt, als neue GRF gespeichert (3,73 GB, verifiziert). Mehrere Änderungen am selben Eintrag bauen aufeinander auf und landen als **eine** Änderung in der Liste. Die Vorschau zeigt den Eintrag **so, wie er gespeichert würde** (inklusive vorgemerkter Änderungen, bei Animationen auch mit einem geänderten Sprite); geänderte Einträge haben in der Liste einen Akzentstreifen, entfernte sind durchgestrichen. Gemessen im Hintergrund (Devserver, echtes Backend, 4.661-Einträge-GRF): Text ersetzen → Vorschau zeigt den neuen Text → als neue GRF speichern (verifiziert, die übrigen Streams bleiben unverändert) → öffnen → neuer Text.
- Einziges npm-Paket: `@tauri-apps/cli` (Entwicklungsabhängigkeit).

## Starten und Bauen
```
cd apps/gui
npm install                  # holt nur die Tauri-CLI
npx tauri dev                # Fenster mit der App
npx tauri build              # Installer/Bundle für das eigene System
cargo test                   # Backend-Tests (Tests mit echten Archiven brauchen RGRF_TESTDATA)
```
Das Bauverzeichnis steht lokal in `.cargo/config.toml` (nicht im Git).
**Prüfen ohne Fenster (Hintergrund):** `cargo run --features devserver --bin devserver -- ui 8766` startet die echte Oberfläche mit dem echten Backend auf `http://127.0.0.1:8766/` (nur localhost, nur für die Entwicklung). Ein Browser, auch ein automatisierter, kann sie bedienen, ohne dass ein Fenster aufgeht; Dateidialoge beantwortet eine Warteschlange (`window.__dialogs.push("/pfad")` vor dem Klick). Fortschrittsanzeigen laufen dort nicht.
Layout ohne App ausprobieren: `python3 -m http.server -d ui 8765`, dann `http://127.0.0.1:8765` öffnen (Mock-Daten).
