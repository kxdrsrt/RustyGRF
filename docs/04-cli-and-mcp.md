# 04 – CLI und MCP

## CLI `rgrf`

Globale Optionen: `--json` (maschinenlesbar, Feld `schema_version`), `--names cp1252|cp949|utf8|raw` (Anzeige und Dateinamen beim Extrahieren, Standard `cp1252` wie GRF Editor, siehe [02-format-notes.md](02-format-notes.md)), `--quiet`, `--threads N`.
Exit-Codes: `0` ok, `1` Fehler, `2` Warnungen (z. B. defekter Eintrag toleriert, verschlüsselter Eintrag übersprungen), `3` Prüfung fehlgeschlagen (`verify` fand Fehler).

**Stand M1/M1b (umgesetzt und getestet):** liest GRF **0x102, 0x103, 0x200 und 0x300** (Version steht in `info`; `key_block` im JSON), dazu **GPF** (ein GRF), **Thor** (`.thor`, Modus 0x30 und 0x21) und **RGZ** (`.rgz`): die Art wird am Inhalt erkannt, jeder Befehl, der ein Archiv nimmt (`info`, `ls`, `find`, `cat`, `extract`, `verify`, `hash`, `diff`, `repack`, `merge`, `lua check`, `map …`, `spr/act … <grf> <pfad>`), nimmt sie alle. `info --json` hat `kind` (`grf`/`thor`/`rgz`), `des_scrambled` (mit dem alten DES verschlüsselte, lesbare Einträge), `removals` (Löschanweisungen eines Patches) und bei Thor `patch` (`merge_into_grf`, `target_grf`). Einträge im `ls --json` haben die Art `des` bzw. `remove`; in der Flag-Spalte von `ls -l` steht `X` für eine Löschanweisung.

Befehle: `info`, `ls`, `find`, `cat`, `extract`, `verify`, `hash`. Muster ohne `*`/`?` sind eine Teilzeichenkette (ohne Groß-/Kleinschreibung, `/` = `\`), mit Platzhaltern ein Glob; reguläre Ausdrücke gibt es noch nicht. `info --codecs` zählt zlib/LZMA (liest ein Byte je Eintrag). `extract` überschreibt nie: Standard bricht bei vorhandenem Ziel ab (`--on-collision skip|rename`, `--overwrite`), verweigert `..`/absolute Pfade und Symlink-Ausbrüche, legt Ordner in Archivreihenfolge an (reproduzierbare Schreibweise auf case-insensitiven Dateisystemen), schreibt beschädigte Einträge mit dem wiederherstellbaren Teil (Warnung, Exit 2) und überspringt Marker und verschlüsselte Einträge.

| Befehl | Zweck |
|---|---|
| `rgrf info <grf>` | Version, Größe, Anzahl Einträge, Kompressionsmethoden, Warnungen; bei 0x300 mit Schlüsselblock auch Gravitys Schutz (`gravity_protection`: geschützte Einträge, Zahl der Archivschlüssel oder warum der Block nicht nutzbar ist). `ls` zeigt geschützte Einträge als `protected`, `cat`/`extract` entschlüsseln sie; Schreibberichte zählen entschlüsselt gespeicherte als `unprotected` (MCP: `protected_decoded`) |
| `rgrf ls <grf> [pattern] [--long]` | Einträge auflisten (Glob oder Teilzeichenkette, Größen, Flags, Offset) |
| `rgrf find <grf> [pattern] [--ext spr,act]` | Suchen (Name, Endung), Ausgabe wie `ls --long` |
| `rgrf cat <grf> <pfad>` | Eintrag auf stdout |
| `rgrf extract <grf> <ziel> [pattern]` | Entpacken (parallel, mit Namenmodus) |
| `rgrf verify <grf>` | Tabelle, Offsets, Überlappungen, Dekompression, Größen, Duplikate |
| `rgrf hash <grf> [pattern]` | CRC32/MD5 je Eintrag |
| `rgrf spr info <spr>` oder `<grf> <pfad>` | **umgesetzt (M7a):** Version, Bilder, Größen, Warnungen eines Sprites (lose Datei oder Eintrag im GRF); `--json` |
| `rgrf spr export <spr>` oder `<grf> <pfad>` `-o <ordner>` | **M7a:** jedes Bild als PNG (`000.png`, ...; Palettenbilder als indiziertes PNG mit Palette, True-Color als RGBA); überschreibt nie ohne `--overwrite` |
| `rgrf spr build <ordner> -o <spr>` | **M7a:** SPR aus den PNGs eines Ordners (nach Namen sortiert); `--version 2.1` (Standard), `2.0`, `1.1`, `1.0`; alle indizierten PNGs müssen dieselbe Palette haben |
| `rgrf act info <act>` oder `<grf> <pfad>` | **umgesetzt (M7b):** Version, Aktionen, Frames, Layer, Sounds, Intervalle; `--json` |
| `rgrf act render <act>` oder `<grf> <pfad>` `[--spr datei] [--action N] [--frame M] [--with <act>]… [--no-anchor] [--gif] [--scale N] -o <ziel>` | **M7b:** Frames als PNG oder (`--gif`) ein animiertes GIF mit der Frame-Zeit der Aktion. Mit `--frame` ist `-o` eine Datei, sonst ein Ordner mit allen Frames der Aktion auf gemeinsamer Leinwand (`000.png`, ...). `--with` zeichnet weitere ACTs darüber (Kopf, Kopfbedeckung; lose Dateien mit `.spr` daneben, bei einem GRF Einträge im selben GRF) und bindet sie über den ersten Anker an die Basis (`--no-anchor` schaltet das ab). `--scale` vergrößert jedes Pixel. Das SPR ist die Datei gleichen Namens (im GRF: gleicher Pfad mit `.spr`); überschreibt nie ohne `--overwrite` |
| `rgrf spr replace <spr> --frame N --png <datei> -o <spr>` | **M7b:** ein Bild ersetzen (`--kind indexed\|rgba`). Ein PNG mit anderer Palette oder in True-Color braucht `--nearest` (nächste Farbe der Sprite-Palette, Alpha unter 128 = transparent) |
| `rgrf spr add <spr> --png <datei> -o <spr>` | **M7b:** Bild anhängen, gibt den neuen Index aus |
| `rgrf spr remove <spr> --frame N [--act <act> --act-output <act>] -o <spr>` | **M7b:** Bild entfernen; mit `--act` werden die Layer nachgeführt (Layer mit dem Bild werden leer, spätere Indizes rücken nach) |
| `rgrf spr set-palette <spr> --pal <pal> -o <spr>` | **M7b:** Palette tauschen (Bilder behalten ihre Indizes) |
| `rgrf spr convert <spr> --to rgba\|indexed [--act <act> --act-output <act>] -o <spr>` | **2026-11-19:** Paletten- in True-Colour-Bilder umwandeln und zurück; die Ebenen der ACT folgen. Zurück ist verlustfrei bei höchstens 255 Farben und ohne halbtransparente Pixel, sonst wird reduziert und die Ausgabe sagt es |
| `rgrf client unused <client\|grf> [--limit N] [--files]` | **2026-11-20:** Dateien in `data\texture`, `sprite`, `wav`, `model`, die kein Text, keine Lua-Tabelle, kein ACT/STR, keine Karte und kein Programm (`.exe`/`.dll`/`.ini` neben den GRFs) nennt, je Ordner mit Größe. Namen werden großzügig gesammelt (klein geschrieben, mit und ohne Endung, ohne Ordner), daher „wahrscheinlich ungenutzt“, nie sicher. Ordner mit `*` (Kartentexturen und -modelle) sind verlässlich, alle anderen (Sprites, Effekte, Oberfläche, Sounds) setzt der Client aus Teilen zusammen: überwiegend Fehlalarme. Ändert nichts; `--json` |
| `rgrf client optimize <ordner> -o <neuer ordner> [--min-psnr 40] [--method lzma] [--recompress] [--dedupe content]` | **2026-11-20:** kleinere Kopie eines Client-Ordners: jede GRF im Ordner wie bei `image reduce` (24-Bit-BMP → 8 Bit ab `--min-psnr`), alles andere wird kopiert; GRFs ohne BMP werden mit `--recompress` neu gepackt, sonst kopiert. Der Quellordner bleibt unverändert, der Zielordner darf nicht darin liegen. Ablauf wie bei `test-smallest` (gespielt, läuft); Schreiboptionen wie `edit` |
| `rgrf image info <bild>` oder `<grf> <pfad>` | **M7d (2026-11-19):** Format (BMP, TGA, PNG), Größe, Bittiefe, Farbzahl, Magenta- und Alpha-Pixel; `--json`. JPEG wird nicht gelesen |
| `rgrf image convert <bild>` oder `<grf> <pfad>` `-o <ziel.png\|ziel.bmp> [--bits 8\|24]` | **M7d:** Umwandeln, das Format folgt der Endung. BMP ist 24 Bit, mit `--bits 8` 256 Farben (gibt die PSNR aus); durchsichtige Pixel (Alpha unter 128) werden Magenta |
| `rgrf image reduce-dir <ordner> -o <neuer ordner> [--min-psnr 40] [--method lzma] [--level 6] [--only GLOB] [--report liste.csv] [--png N] [--jpegtran PFAD] [--overwrite]` | **2026-11-20:** `reduce` für einen **Ordner**: schreibt eine vollständige Kopie, in der 24-Bit-BMPs 8 Bit sind, wo die Qualität hält und die (mit `--method` komprimierte) Datei kleiner wird; die Quelle wird nur gelesen. Der Ausgabeordner darf nicht in der Quelle liegen und muss leer sein (oder `--overwrite`). Dateinamen bleiben byteweise erhalten. **Gemessen** (Mac): `grf/core` (4.706 Dateien) in 3 s, `grf/data-official` (202.365 Dateien, 15 GB) in 85 s, 25.255 BMPs, gleiche Zahlen wie `reduce` am Archiv. **2026-11-21:** `--png N` macht PNGs verlustfrei kleiner (Zeilenfilter neu gewählt, Zopfli mit N Durchläufen, Text-/Zeit-/Exif-Chunks entfernt; geprüft, dass das Bild gleich bleibt; verschachtelte und animierte PNGs bleiben), `--jpegtran PFAD` ebenso für JPEGs (`jpegtran -copy none -optimize`, Baseline) |
| `rgrf image reduce <grf> -o <grf> [--min-psnr 40] [--only GLOB] [--recompress] [--report liste.csv] [--dry-run]` | **M7d:** Kopie des Archivs, in der jede 16/24/32-Bit-BMP als 8-Bit-BMP gespeichert ist, wenn das Bild mindestens `--min-psnr` dB behält **und** die gespeicherte (komprimierte) Datei kleiner wird. Magenta bleibt exakt, keine andere Farbe wird durchsichtig, Bilder mit höchstens 256 Farben verlieren nichts. Bericht: verkleinert, verlustfrei, schlechteste PSNR, gespeicherte Größe vorher/nachher, behaltene nach Grund; Schreiboptionen wie `edit`. Mit `--method lzma` nutzen nur die neuen BMPs LZMA, unveränderte Streams werden kopiert; `--recompress` (braucht `--method`) kodiert alle Einträge neu (zlib-Archiv → LZMA); `--report` schreibt eine CSV (Pfad, PSNR, Größe vorher/nachher) aller verkleinerten Bilder |
| `rgrf act translate <act> --dx X --dy Y [--action N] -o <act>` | **M7b:** alle Layer und Anker verschieben |
| `rgrf pal info\|extract\|png\|from-png\|set\|adjust\|sheet …` | **M7b Palette:** `info` (256 Farben), `extract` (Palette eines SPR als `.pal`), `png` (16×16-Bild der Palette) und `from-png` (indiziertes PNG oder dieses Bild → `.pal`), `set --color N=RRGGBB`, `adjust` (Farbton, Sättigung, Helligkeit eines Bereichs), `sheet` (ein Frame mit der eigenen und mit jeder `--pal` in einem PNG) |
| `rgrf act interval <act> --action N --value V -o <act>` | **M7b:** Frame-Zeit (Einheit 25 ms) |
| `rgrf act interpolate <act> --action N [--frame F] [--count K] [--smooth] [--wrap] [--keep-speed] -o <act>` | **2026-11-19:** Zwischenframes (1–20 je Paar): Versatz, Skalierung, Drehung, Farbe, Anker werden in Schritten von einem Frame zum nächsten gemischt (Bild und Spiegelung wechseln zur Hälfte, Sounds bleiben bei den Originalen). Ohne `--frame` die ganze Aktion; `--wrap` blendet den letzten Frame zurück in den ersten; `--keep-speed` kürzt die Frame-Zeit (mindestens 25 ms), damit die Aktion gleich lang dauert; `--smooth` bremst an den Enden |
| `rgrf act layer <act> [--action N [--frame F [--layer L]]] [--color RRGGBB[AA]] [--scale S \| --scale-x X --scale-y Y] [--rotation GRAD] [--mirror true\|false] [--flip] -o <act>` | Layer-Feinbearbeitung: Farbmaske (Alpha = durchscheinend), Skalierung, Drehung, Spiegeln; Farbe/Skalierung/Drehung ab ACT 2.0, getrennte Y-Skalierung ab 2.4 (sonst Fehler) |
| `rgrf act sound <act> --action N --frame F --sound <name.wav\|none> -o <act>` | Sound je Frame setzen oder entfernen (Name wird in die Tabelle eingetragen; ab ACT 2.1) |
| `rgrf act copy-action <act> --from N --to M -o <act>` / `remove-action --action N` | **M7b:** Aktion kopieren/entfernen |

| `rgrf lua check <datei \| ordner \| grf> [muster]` | **umgesetzt (M7c):** Lua-5.1-Syntaxprüfung von `.lub`/`.lua` (Datei, Ordner rekursiv oder Dateien eines GRF) mit Zeilennummer; kompilierte Dateien werden gezählt, nicht geprüft. Exit 0 ok, 3 Fehler |
| `rgrf lua compile <text.lua> -o <datei.lub> [--lua-version 5.1\|5.0] [--strip] [--encoding auto\|cp949\|utf8] [--name N] [--overwrite]` | **2026-11-19:** Lua-5.1-Text zu einer `.lub` im Layout des Clients (32-Bit), dieselben Bytes wie das echte `luac` 5.1 (gemessen, siehe 09-formats.md); koreanischer Text wird wieder CP949. Ablauf zum Ändern: `lua decompile <grf> --entry … -o x.lua`, bearbeiten, `lua compile x.lua -o x.lub`, mit `edit`/`merge` ins GRF. Mit `--lua-version 5.0` kompiliert der 5.0.3-Port (die 62 5.0-Dateien der kRO-`data.grf`), ebenfalls dieselben Bytes wie das echte `luac` 5.0.3 |
| `rgrf client refs <client-ordner oder grf> [--only act\|str] [--limit N] [--files]` | **2026-11-19:** prüft, was Animationen (`.act`) und Effekte (`.str`) nennen: das `.spr` neben der Animation, die Bildnummern ihrer Ebenen (palette/true colour) gegen das Sprite, die Sounds der Frames unter `data\wav\` (ab ACT 2.1; „atk“ ist die Treffer-Markierung und keine Datei) und die Texturen eines Effekts (neben ihm, dann `data\texture\effect\`). Bei einem Ordner gilt wie im Client das erste Archiv; lose `data`-Dateien zählen mit. Ausgabe: Zählung je Art, fehlende Sprites nach Ordner gezählt (`--files`: jede Datei), sonst die Einzelfälle (`--limit`); Exit 0 nichts fehlt, 3 Meldungen. **Auf einer einzelnen GRF viele Fehlalarme**, wenn Sprites in einer anderen liegen: den Client prüfen. Nicht geprüft: Namen aus Lua-Tabellen |
| `rgrf client check <client-ordner> [--no-lua]` | **M7c:** liest `DATA.INI` und die Archive wie der Client und meldet: fehlende Archive, nicht eingetragene Archive, Dateien, die ein Archiv mit niedrigerem Index verdeckt, **lose Dateien im `data`-Ordner, die ein Archiv verdeckt** (Client ignoriert sie), alle Server-Einträge (`sclientinfo.xml`) je Kopie und Abweichungen, LZMA ohne `cps.dll`, ein `SystemEN`-Verweis im Programm ohne Ordner, Lua-Syntaxfehler der wirklich geladenen Dateien. Exit 0 ok, 2 Warnungen, 3 Fehler |
| `--password <text>` / `--key-file <datei>` (für alle Befehle; Passwort auch aus `RGRF_PASSWORD`) | **2026-11-19:** Schlüssel von GRF Editors Verschlüsselung: öffnet verschlüsselte Archive (auch mit verschlüsselter Dateitabelle). Ohne Schlüssel öffnet ein verschlüsseltes Archiv trotzdem, die Einträge sind „verschlüsselt“ (`info` zeigt es, `extract` überspringt sie) |
| `rgrf --password … --encrypt build\|repack\|merge\|patch …` | verschlüsselt die Ausgabe (nur 0x200, wie GRF Editor); `repack` mit Schlüssel ohne `--encrypt` schreibt entschlüsselt. Quellen mit Schlüssel werden vorher entschlüsselt, ein anderer Schlüssel ist also möglich |
| `rgrf --password … key create -o <datei.grfkey>` | schreibt eine Schlüsseldatei, die GRF Editor und `--key-file` lesen |
| `rgrf --password … client encrypt <client.exe> [--cps-dll <cps.dll>] -o <ordner> [--no-rename] [--skip-resource-check]` | schreibt die gepatchte EXE und die DLL mit dem Schlüssel; die Vorlage `cps.dll` von GRF Editor (`GRFEditor/Files/cps.dll`, 176 KB) ist eingebaut (mit Tokeiburus Erlaubnis), `--cps-dll` nimmt eine andere. Beide Dateien in den Client-Ordner, die GRFs mit demselben Schlüssel verschlüsseln |

| `rgrf map flat <client-ordner \| grf> [karte…] -o <grf> [--flatten] [--remove-light] [--remove-shadow] [--remove-color] [--gat-shadows] [--reset-light] [--remove-objects] [--remove-water]` | **2026-11-20:** GRF Editors „Flat maps maker“: schreibt ein kleines Archiv nur mit den geänderten RSW/GND/GAT der Karten (vor die anderen in `DATA.INI`); ohne Option `--flatten --remove-light --remove-shadow`. Boden und Wasser folgen den Namen in der RSW. Exit 3, wenn Karten übersprungen wurden. **Gemessen:** kRO-`data.grf`, alle 1.029 Karten in 6,9 s, 100 MB, `verify` ohne Fehler |

Bei einem Client-Ordner zählen `DATA.INI`-Reihenfolge und lose Dateien. Exit 0 ok, 3 Probleme |

Die Bearbeiten-Befehle lesen eine lose Datei (oder `<grf> <pfad>`) und schreiben **immer eine neue Datei**; sie ändern nie die Eingabe und überschreiben nichts ohne `--overwrite`. Zurück ins GRF kommt das Ergebnis mit `rgrf build`, `merge` oder `patch`.
| `rgrf build <ordner> -o <grf>` | **umgesetzt (M2):** GRF aus Ordner (Ordner = Archivwurzel, enthält z. B. `data/`); gleiche Optionen wie `repack` (`--method`, `--level`, `--format` Standard 0x200, `--align/--no-align`, `--dedupe` = gleicher Inhalt teilt einen Block, `--no-verify`, `--overwrite`, `--dry-run`); Dateinamen NFC, `.DS_Store`/`._*`/`Thumbs.db`/`desktop.ini`/Symlinks werden übersprungen und gemeldet; Fehler bei nicht darstellbaren Namen, Groß-/Kleinschreibungs-Kollisionen, Dateien ≥ 4 GiB, Ausgabe im Quellordner |
| `rgrf repack <grf> -o <grf>` | **umgesetzt (M2):** neu komprimieren/umformatieren, Inhalt unverändert; `--method zlib\|zopfli\|lzma`, `--level`, `--format 0x200\|0x300`, `--align/--no-align`, `--dedupe none\|source\|content`, `--recompress-all`, `--no-verify`, `--overwrite`, `--dry-run` |

| `rgrf merge <grf> <grf>… -o <grf>` | **umgesetzt (M3):** das **erste** Archiv gewinnt je Pfad (wie der niedrigste Index in `DATA.INI`: eigene Custom-GRFs zuerst, `data.grf` zuletzt); Ausgabereihenfolge = Reihenfolge des Archivs mit der niedrigsten Priorität, dann neue Pfade der nächsten; **ohne `--method` werden alle Ströme unverändert kopiert** (nichts wird neu komprimiert, deshalb schnell; geprüft wird, dass jeder kopierte Strom byteidentisch ankommt), mit `--method` wird neu komprimiert und der neue Strom behalten, wo er kleiner ist; **`--replace-only`**: das letzte Archiv ist die Basis, frühere ersetzen dessen Dateien, fügen aber keine neuen Pfade hinzu (Übersetzung in ein GRF einspielen, siehe `docs/08-translation.md`); bei Ersatz bleibt die Schreibweise der Basis; sonst wie `repack` (`--level`, `--format` Standard 0x300, wenn eine Quelle 0x300 ist, sonst 0x200, `--dedupe`, …); leere Marker werden nicht kopiert (gemeldet); je Quelle: Dateien / übernommen / überschrieben |

Dieselbe Funktion (`rgrf_core::edit`) nutzt die GUI. **Gemessen:** `rdata.grf` (290 MB, 24.756 Einträge) mit 1 neuer Datei und 1 entfernten: 0,59 s, 24.755 Ströme unverändert, `verify` 0 Fehler, `diff` zeigt genau diese zwei Unterschiede. | `rgrf crypt <grf> -o <neu> [--encrypt-entry MUSTER]… [--decrypt-entry MUSTER]… [--encrypt-table\|--decrypt-table]` | **2026-11-21:** GRF Editors „Encrypt“/„Decrypt“ auf einzelnen Dateien und „Encrypt File Table“ (nur 0x200/0x300, Passwort mit `--password`/`--key-file`, öffnet auch eine verschlüsselte Quelle); alles andere behält seinen Zustand (die Tabelle ebenfalls, wenn kein Schalter gegeben ist); Blöcke werden nicht geteilt, das Ergebnis kann größer werden |

Verhalten:
- Schreibbefehle arbeiten in eine temporäre Datei, prüfen sie (`verify`) und benennen dann um.
- `--dry-run` zeigt, was passieren würde.
- `--json` hat ein stabiles Schema (Versionsfeld).

## MCP-Server `rgrf-mcp`

**Umgesetzt (M4).** Transport stdio (zeilenweises JSON-RPC 2.0, MCP-Version 2025-06-18; ältere 2025-03-26 und 2024-11-05 werden ausgehandelt), nur Tools. Start: `rgrf-mcp [--allow-write <ordner>]… [--allow-read <ordner>]…`. Eingebunden in `.vscode/mcp.json` als `rustygrf` (Schreibordner `~/build/rgrf-out`). Das offizielle Rust-SDK (`rmcp`, mit tokio) wird bewusst nicht genutzt: das Protokoll für reine Tools ist klein, und so bleiben die Abhängigkeiten gering.

Jedes Ergebnis kommt als `structuredContent` (JSON-Objekt) und als Text. Fehler einer Anfrage (Archiv fehlt, Pfad nicht erlaubt, falsches Argument) kommen als `isError: true` mit klarer Meldung, damit der Agent sich korrigieren kann; ein unbekanntes Tool oder eine unbekannte Methode ist ein JSON-RPC-Fehler. Argumente werden gegen dieselbe Tabelle geprüft, aus der das JSON-Schema erzeugt wird (unbekannte, fehlende, falsch typisierte Argumente werden abgelehnt).

Sicherheit (umgesetzt und getestet):
- **Nur Lesen als Standard.** Die schreibenden Tools werden nur angeboten (und angenommen), wenn mindestens ein `--allow-write` gegeben ist.
- Schreiben nur unterhalb der erlaubten Ordner; `..` wird abgelehnt, Symlinks werden vor der Prüfung aufgelöst (kein Ausbruch über Ordner- oder Datei-Symlinks), ein Symlink als Ziel wird abgelehnt.
- Vorhandene Dateien werden nur mit `overwrite=true` ersetzt, Ordner nie; eine Ausgabe darf nie eines ihrer Eingabearchive sein; alle Schreibbefehle gehen über temporäre Datei, Rückprüfung und Umbenennen.
- Lesen geht überall (Entscheidung zu Punkt 20); `--allow-read` beschränkt es auf die genannten Ordner (plus Schreibordner).
- Fremde Archive: Einträge über 256 MiB werden nicht dekodiert, jede Antwort ist begrenzt (Seiten, `max_bytes`, `limit`) und mit `truncated` markiert; ein Absturz in einem Tool wird abgefangen und als Fehler gemeldet.
- Abbruch: `notifications/cancelled` stoppt einen laufenden Aufruf (gemessen: Zopfli-Build mit 150 Dateien wird in unter 4 s beendet, keine halbe Datei, keine temporäre Datei bleibt), er bekommt dann keine Antwort. Fortschritt kommt als `notifications/progress`, wenn der Client einen `progressToken` mitschickt.

**Verschlüsselte Archive:** der MCP-Server liest das Passwort aus seiner Umgebung (`RGRF_PASSWORD`, oder `RGRF_KEY_FILE` für eine `.grfkey`), nie aus einem Tool-Argument, damit es nicht im Chat steht. Mit dem Schlüssel öffnen alle Werkzeuge verschlüsselte Archive; `grf_build`, `grf_repack`, `grf_merge`, `grf_patch` haben `encrypt` (nur 0x200).

Grenzen: Ein Aufruf läuft, bevor der nächste bearbeitet wird (ein Client kann während `grf_build` nicht gleichzeitig `grf_list` abfragen); sehr lange Aufrufe (Merge der 5,7-GB-Archive, Zopfli) können Zeitlimits mancher Clients überschreiten, Fortschrittsmeldungen helfen dort. Eine Eingabe pro Zeile; die Länge einer Zeile ist nicht begrenzt (der Client ist vertrauenswürdig, nur die Archive nicht).

Typische Anfragen an den Agenten: "Welche Dateien aus `rdata` überschreiben `data`?" (`grf_diff`), "Baue `cdata` mit LZMA und vergleiche die Größe" (`grf_build`, `grf_info`), "Suche in `data` alle Dateien mit `job4`" (`grf_list`).
